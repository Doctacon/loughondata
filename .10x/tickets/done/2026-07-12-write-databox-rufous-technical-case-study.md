# Write the Databox-to-Rufous technical case study

## Scope

Write and publish a new Lough on Data technical case study, working title **“How Databox Became the Warehouse Behind Rufous.”** The article explains Databox’s evolution since 2026-07-06 through one causal argument:

> Parallel local ingestion makes a multi-source warehouse practical; a reviewed schema → taxonomy → ontology → CDM → SQLMesh workflow turns provider-shaped raw data into durable domain concepts; Rufous demonstrates that those concepts can support a real product surface.

Cover these sections:

1. The problem: a local multi-source DuckDB warehouse cannot become a product foundation if refresh is sequential, fragile, or provider-shaped.
2. Quack: one DuckDB-owning server with concurrent hermetic dlt clients, followed by SQLMesh only after successful source completion.
3. Semantics-first modeling: raw dlt schema → annotated taxonomy → ontology → Kimball CDM → SQLMesh transformations.
4. Rufous as reference consumer: Arizona bird catalog, trip planning, alerts/calendar, and Field Map use the warehouse without making Rufous itself the warehouse’s core purpose.
5. Contract hardening: the canonical seven-source registry, source-derived CI, and modeling completeness as proof the workflow remains trustworthy after product pressure.
6. Limits: distinguish warehouse-enabled product capabilities from independent UI/product work; do not claim all Rufous behavior is generated by the semantic workflow.
